# Hosting an Anchor instance

This guide will walk you through the steps to deploy your own Anchor instance, the Novarum homeserver.

:::caution
Novarum is in heavy development and daily updates are frequent. Deployment details may change as the project evolves. That being said, we attempt to push the least amount of breaking configuration changes.
:::

## Prerequisites

- A Linux server with Docker and Docker Compose installed. Virtually any hardware will work.
- Solid network connection and public IP: A Livekit server will be set up to handle voice calls.
- A domain name for your server. We'll be using `piedpiper.com` as an example.

  <TabItem label="config.toml">
    This is Anchor's configuration file.
    ```toml
    [server]
    database_url = "postgresql://novarum:Y0U_SH0ULD_CHANG3_TH1S@postgres:5432/novarum"
    homeserver = "piedpiper.com"
    base_url = "https://piedpiper.com"

    [federation]
    key_dir = "./keys"

    [voice]
    livekit_url = "wss://lk.piedpiper.com"
    livekit_key = "RANDOMLY_GENERATED_KEY"
    livekit_secret = "RANDOMLY_GENERATED_SECRET"

    [files]
    s3_access_key = "READ_BELOW_FOR_GENERATION"
    s3_secret_key = "READ_BELOW_FOR_GENERATION"
    s3_bucket = "novarum"
    s3_endpoint = "http://garage:3900"
    s3_public_endpoint = "https://cdn.piedpiper.com"
    s3_region = "garage"
    s3_cors_origins = ["https://app.novarum.me"]

    [email]
    smtp_host = "smtp.resend.com"
    smtp_secure = true
    smtp_user = "resend"
    smtp_pass = "REPLACE_WITH_YOUR_RESEND_API_KEY"
    from_email = "novarum@piedpiper.com"

    [misc]
    otp_pepper = "RANDOMLY_GENERATED_PEPPER"
    # controls if the server saves attachment thumbnails.
    # this is here in case you want to save space by getting it cached through a CDN
    save_attachment_thumbnails = true

    # optional: see "Routing outbound requests through a proxy or VPN" below
    [network]
    proxy_url = "http://proxy:3128"
    ```

    A few notes:
      - `s3_endpoint` is the internal Garage address the server uses for its own requests and must bypass any proxy/CDN in front of Garage. `s3_public_endpoint` is only used to build the presigned download URLs handed to clients and should be the public CDN URL. If they are the same, omit `s3_public_endpoint`.
      - Keep in mind that, automatically, a S3 CORS origin will be added to enable Novarum Desktop uploads. There is currently no way to disable it, though we highly doubt you would want to.
      - We recommend using Resend for email delivery because its free plan is very generous and probably enough for most deployments, though feel free to swap the SMTP credentials with your own.
      - 5GB is logistically the current upload limit as multipart presigned uploads haven't been implemented yet. That's the ceiling for a single presigned PUT; if uploads still go through a proxy, its body size limit applies first.

## Secret generation

A few secrets must be generated:

<Tabs>
  <TabItem label="Anchor">
    Anchor requires a randomly generated OTP pepper to store OTPs securely in the database. You can
    generate it with `openssl rand -hex 16`
  </TabItem>
  <TabItem label="Livekit">
    Livekit requires a key and secret. You can generate them with the following command: ```bash
    openssl rand -hex 16 ``` This will generate a random 32-character hexadecimal string. Use this
    for both the key and secret in `config.toml` and `livekit.yaml`.
  </TabItem>
  <TabItem label="Garage">
    Garage requires an RPC secret, access key, and secret key. You can generate them with the
    following commands: ```bash openssl rand -hex 32 # For RPC secret openssl rand -base64 32 # For
    Access key openssl rand -base64 32 # For Secret key ``` Use these generated values in
    `garage.toml` and `compose.yml`.
  </TabItem>
  <TabItem label="Postgres">
    Generate a strong password for the Postgres database. You can use the following command: ```bash
    openssl rand -base64 32 ``` Use this password in `compose.yml` for the `postgres` service, and
    wire it up in the `config.toml` file for Anchor's database connection.
  </TabItem>
</Tabs>

## Ports and locations

We recommend running everything though a reverse proxy, such as Caddy, but the demo server runs on Cloudflare Tunnels, so we'll be demonstrating that.

| Domain            | Points to             |
| ----------------- | --------------------- |
| piedpiper.com     | http://localhost:5049 |
| lk.piedpiper.com  | http://localhost:7880 |
| cdn.piedpiper.com | http://localhost:3900 |

You'll also need to open `50100-50200/udp` in your firewall for WebRTC connections to work properly.

## Handling different hosts

Anchor sometimes needs to be hosted on a different host than what the homeserver URL is.  
For example, the `novarum.me` Anchor isn't hosted in the same place, and is instead on `anchor.novarum.me`.

It should be relatively simple to handle these cases:

1. Run the Anchor on another host, such as `anchor.novarum.me`.
2. Proxy only the `/.well-known/anchor/info` endpoint to `novarum.me`, so clients can discover the actual homeserver URL. We use Cloudflare Workers to do this.
3. Set `homeserver` to `novarum.me` and `base_url` to `https://anchor.novarum.me` in the `config.toml` file.

## Routing outbound requests through a proxy or VPN

Some hosts restrict or censor outbound internet access. Anchor makes outbound requests for
federation (talking to other Anchors), the emoji CDN, S3-compatible storage, and LiveKit's REST
API — all over HTTP(S). If any of that gets blocked, you have two options:

<Tabs>
  <TabItem label="Forward proxy (HTTP-only)">
    Set `proxy_url` under `[network]` in `config.toml` to any HTTP(S) forward proxy Anchor can
    reach (a `tinyproxy`/`privoxy` container, a proxy your VPN provider exposes, etc). Every
    outbound `fetch` and S3 request Anchor makes will go through it:
    ```toml
    [network]
    proxy_url = "http://proxy:3128"
    ```
    This is the lightest option, but it only covers HTTP(S) traffic. Postgres and SMTP use raw
    sockets, not `fetch`, so they're unaffected — the database and mail server still need to be
    reachable directly.
  </TabItem>
  <TabItem label="Full tunnel (VPN or Cloudflare WARP)">
    To route *everything* Anchor sends — Postgres, SMTP, and HTTP(S) alike — put the `anchor`
    container on a VPN container's network namespace instead, with `network_mode: "service:<vpn
    service>"`. Sharing a network namespace this way means Anchor uses that container's routes
    and interfaces directly, so no `config.toml` changes are needed.

    For Cloudflare WARP specifically, generate a free WireGuard profile for it with
    [`wgcf`](https://github.com/ViRb3/wgcf) (`wgcf register && wgcf generate`, which writes
    `wgcf-profile.conf`), then feed that profile into a standard WireGuard container, such as
    [`linuxserver/wireguard`](https://github.com/linuxserver/docker-wireguard) run as a client:
    ```yml
    services:
      wireguard:
        image: lscr.io/linuxserver/wireguard:latest
        container_name: wireguard
        restart: unless-stopped
        cap_add:
          - NET_ADMIN
        environment:
          - PUID=1000
          - PGID=1000
          - TZ=Etc/UTC
        volumes:
          # wgcf-profile.conf goes in here, renamed to wg_confs/wg0.conf
          - ./wireguard:/config
        sysctls:
          - net.ipv4.conf.all.src_valid_mark=1

      anchor:
        image: ghcr.io/novarumsocial/anchor:latest
        container_name: anchor
        restart: unless-stopped
        network_mode: 'service:wireguard'
        depends_on:
          - wireguard
          - postgres
          - livekit
        volumes:
          - ./config.toml:/app/config.toml:ro
          - ./keys:/app/keys
    ```
    Don't set `PEERS` on the `wireguard` service — that switches it into server mode. Because
    `anchor` shares `wireguard`'s network namespace, its published ports (`5049`, etc.) also move
    to the `wireguard` service — point your reverse proxy there instead. Any other VPN's Docker
    client (a commercial provider's image, Tailscale, …) works the same way: start it as its own
    service and set `network_mode: "service:<that service>"` on `anchor`.
  </TabItem>
</Tabs>

# (Optional) Hosting the frontend

Novarum's frontend is a simple SvelteKit app with the `static` adapter. [app.novarum.me](https://app.novarum.me) is hosted on Vercel.  
Because it's a single-page app, you need to redirect any request to `index.html` so that the frontend can handle routing. The guides below are adapted for this!

One last note: `novarum.me` is only set up to support CORS at `localhost:8080`. Keep this in mind so you can test the app after deploying it.

## Hosting on Vercel

1. Fork the repo
2. Open the Vercel dashboard and create a new project.
3. Select the forked repo and change the "Root Directory" to `apps/frontend`.
4. Enjoy!

## Hosting with Docker

The following docker image is based on the Caddy hosting guide below, but packaged in a fancy Docker image.

<Code
  lang="yml"
  title="docker-compose.yml"
  code={`services:
  frontend:
    image: ghcr.io/novarumsocial/frontend:latest
    ports:
      - '8080:8080'
    restart: unless-stopped`}
/>

## Hosting on Caddy

1. Clone the repo and `cd apps/frontend`
2. Install all dependencies with `bun install`
3. Build the website with `bun build`
4. Run the caddy server with `caddy run -c Caddyfile`
5. Access the website at `http://localhost:8080`

## Hosting with `npx serve`

1. Clone the repo and `cd apps/frontend`
2. Install all dependencies with `bun install`
3. Build the website with `bun build`
4. Run the server with `bunx serve ./build/ -p 8080 -s`
5. Access the website at `http://localhost:8080`
